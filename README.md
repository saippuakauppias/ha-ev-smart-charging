# EV Smart Night Charging — блюпринт для Home Assistant

[![CI](https://github.com/saippuakauppias/ha-ev-smart-charging/actions/workflows/ci.yml/badge.svg)](https://github.com/saippuakauppias/ha-ev-smart-charging/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Блюпринт автоматизации, который заряжает электромобиль или PHEV в заданном ночном
окне и **динамически подбирает ток**, чтобы зарядка равномерно растянулась до
времени окончания, а не «выстреливала» максимумом в первый час и потом стояла.

Меньший ток — меньше нагрев кабеля и бортового зарядного устройства, мягче режим
для батареи и ровнее нагрузка на домашнюю сеть. При этом машина всё равно готова
к нужному времени.

Блюпринт не привязан к конкретной марке автомобиля или модели зарядной станции:
все сущности выбираются в интерфейсе.

```
23:00  ─────────────────────────────────────────────────────────  07:00
       ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  28 A   ← «зарядить как можно быстрее»
       ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  14 A   ← этот блюпринт
```

## Что умеет

- **Окно зарядки** с точностью до минуты, корректно переходит через полночь;
  можно выбрать дни недели. Удобно совмещать с ночной зоной двухтарифного счётчика.
- **Динамический подбор тока**: раз в 10–30 минут блюпринт сверяет факт с планом
  и корректирует уставку. Зимой ток сам вырастет, потому что регулятор увидит
  отставание от графика.
- **Жёсткие границы тока** — минимум и максимум задаются явно, выйти за них
  автоматизация не может ни при каких расчётах.
- **Целевой процент заряда** вплоть до 100 включительно.
- **Запуск только когда машина дома** — зона выбирается из зон Home Assistant.
  Если машина приехала посреди ночи или GPS сбоил, зарядка стартует сразу после
  появления в зоне, а не ждёт следующего окна.
- **Работа без связи с машиной**: при недоступных данных о заряде автоматизация
  не падает, а продолжает заряжать по запасному плану.
- **Троттлинг команд** — станции, плохо переносящие частые команды, получают
  не больше одной команды в заданный интервал.
- **Аварийная дозарядка** ниже критического процента вне окна — максимальным
  током и с запасом над порогом, чтобы не остановиться ровно на нём.
- **Режим холодной погоды**: ниже заданной температуры растяжка отключается.
- **Контроль исправности**: «включено, но ток не идёт», неисправность станции,
  протухшие данные — всё уходит в настраиваемые действия-уведомления.

## Как работает регулятор

Раз в N минут:

```
нужно_кВтч   = (цель % − текущий %) / 100 × ёмкость / КПД
осталось_ч   = до конца окна − резерв          (переход через полночь учтён;
                                               вне окна растяжки нет)
ток          = нужно_кВтч × 1000 / осталось_ч / (U × число фаз)
ток          = округлить вверх до шага, зажать в [минимум, максимум]
```

Ключевое — это замкнутая обратная связь. Если машина берёт меньше, чем задано,
на следующем тике процент окажется ниже плана: `нужно_кВтч` останется прежним,
а `осталось_ч` уменьшится, и ток вырастет. Тот же механизм компенсирует неточность
введённой ёмкости и КПД, поэтому паспортных значений достаточно.

Есть два независимых способа посчитать, сколько ещё нужно залить:

| Источник плана | Что нужно | Когда применяется |
|---|---|---|
| `soc` | сенсор процента заряда машины | основной |
| `energy` | сенсор энергии сессии станции + цель в кВт·ч | если процент недоступен |
| `none` | ничего | резервный ток до конца окна |

Второй способ работает вообще без интеграции с автомобилем.

## Установка

### Вариант 1 — импорт по ссылке (рекомендуется)

1. Настройки → Автоматизации и сцены → Блюпринты → **Импортировать блюпринт**.
2. Вставьте ссылку на файл блюпринта в этом репозитории:

```
https://github.com/saippuakauppias/ha-ev-smart-charging/blob/main/blueprints/automation/ev_smart_charging/ev_smart_night_charging.yaml
```

### Вариант 2 — вручную

Скопируйте `blueprints/automation/ev_smart_charging/ev_smart_night_charging.yaml`
в `config/blueprints/automation/ev_smart_charging/` и перезагрузите автоматизации.

**Требуется Home Assistant 2024.10 или новее** — блюпринт использует секции
в настройках и современный синтаксис триггеров.

## Быстрый старт

Обязательных полей всего три:

| Поле | Что выбрать |
|---|---|
| Выключатель зарядки | `switch`, разрешающий выдачу тока |
| Уставка тока | `number` с током в амперах |
| Сенсор статуса станции | текстовый сенсор со значениями вида `charging`, `charged` |

Всё остальное имеет разумные значения по умолчанию. С такой минимальной
настройкой блюпринт будет заряжать резервным током в заданном окне — уже
полезно, но без растяжки. Чтобы включить регулятор, добавьте сенсор процента
заряда батареи **или** сенсор энергии сессии с целью в кВт·ч.

После импорта обязательно проверьте раздел **«Расшифровка статусов станции»**:
значения по умолчанию (`available`, `charging`, `charged`, `fault`) подходят
не всем станциям. Посмотреть свои можно в истории сенсора статуса.

## Настройка

Параметры сгруппированы по секциям; каждое поле в интерфейсе снабжено подробным
описанием. Ниже — то, что стоит настроить в первую очередь.

### Ток и электрика

| Параметр | По умолчанию | Комментарий |
|---|---|---|
| Минимальный ток | 6 A | Стандарт однофазной зарядки начинается с 6 А |
| Максимальный ток | 28 A | Ориентируйтесь на самое слабое звено цепи |
| Дискретность тока | 1 A | С каким шагом станция принимает значения |
| Запасное напряжение | 230 В | Только когда измерить нечем — см. ниже |
| КПД зарядки | 88 % | Зимой 80–85, летом 90–93; занижать безопаснее |
| Минимальное изменение для записи | 3 A | Гасит косметические правки уставки |

Напряжение берётся из трёх источников по приоритету:

1. сенсор напряжения станции;
2. вычисление из мощности и фактического тока — `P / (I × число фаз)`;
3. запасное значение из настроек.

Оба измерения принимаются только в диапазоне 175–280 В. Ниже 175 В зарядка
в любом случае должна отключаться по недопустимому напряжению, так что такие
показания означают простой или неисправность. Верхняя граница отсекает мусор
вроде милливольт, принятых за вольты: завышенное напряжение занизило бы
расчётный ток до минимума на всю ночь.

Третий пункт нужен прежде всего для одного случая: в момент принятия решения
о старте станция ещё обесточена и измерять нечего, а ток для первой команды
посчитать уже надо. Со второго пересчёта в дело идут живые данные — если,
конечно, соответствующие сенсоры вообще заданы.

### Окно зарядки

Если у вас двухтарифный счётчик, окно имеет смысл совместить с ночной зоной.
**Точное время начала и окончания уточните у своей энергосбытовой организации** —
оно различается по регионам и зависит от модели счётчика. Небольшой запас после
начала льготной зоны не помешает: часы счётчика и Home Assistant могут расходиться.

Параметр «Резерв времени» строит план так, чтобы закончить раньше конца окна.
Компенсирует замедление заряда на последних процентах и заодно страхует
от заезда в дорогую зону.

### Троттлинг команд

Повторная запись тока не происходит раньше, чем через заданный интервал
(по умолчанию 60 секунд) после предыдущего изменения. Контроль ведётся
по `last_changed` самой сущности, поэтому переживает перезапуск Home Assistant
и не требует вспомогательных элементов.

Троттлинг реализован **проверкой, а не паузой**: если интервал ещё не вышел,
запись откладывается до следующего пересчёта. Блокирующая пауза здесь не годится —
автоматизация работает в режиме `restart`, и любой триггер (например, смена
статуса станции) оборвал бы незавершённую паузу вместе с командой, которая должна
была идти после неё. Регулятор при этом молча перестал бы работать.

Два исключения:

- **первая команда сессии** идёт без ожидания — иначе старт зарядки
  откладывался бы на весь интервал;
- **выключение зарядки** — команда безопасности, идёт первой и без задержки.

## Отказоустойчивость

Достоверность данных о заряде проверяется по трём признакам, строго в этом порядке:

| Проверка | Что означает | Что делает блюпринт |
|---|---|---|
| Сущность недоступна | Чаще всего слетела авторизация интеграции | `car_data_unavailable_check_integration_auth` |
| Данные устарели | Машина давно не выходила на связь | `car_data_stale` |
| Процент «замёрз» | Значение не меняется, хотя ток идёт | `car_data_frozen` |

Третья проверка нужна потому, что многие облачные интеграции при пропаже связи
с машиной **не уходят в `unavailable`**, а продолжают отдавать последнее
закэшированное значение сколь угодно долго. Для регулятора это худший из отказов:
замёрзший процент заставил бы держать максимальный ток всю ночь.

При любом из трёх зарядка **продолжается** — план переключается на энергию сессии
либо на резервный ток, а причина уходит в уведомление.

Аналогично с геолокацией: потеря позиции запрещает старт новой сессии, но не рвёт
уже идущую. Это отличает «трекер замолчал» от «машина уехала».

Тот же принцип применён к статусу станции. Если сенсор статуса стал нечитаемым
(`unknown` / `unavailable`), новая сессия **не начинается** — отличить
подключённый кабель от пустой розетки нечем, а включение вслепую вдобавок
подняло бы ложную тревогу «включено, но тока нет». Уже идущая зарядка при этом
не прерывается.

Отдельно блюпринт защищён от нескольких «тихих» ошибок настройки, каждая
из которых иначе навсегда и без единого сообщения отключила бы зарядку:

| Ситуация | Что было бы | Что делает блюпринт |
|---|---|---|
| В поле энергии сессии указан накопительный счётчик | «Уже залито 4500 кВт·ч» → цель считается достигнутой | Считает сенсор недоступным и заряжает по резервному плану |
| Сняты все галочки дней недели | Окно не откроется никогда | Трактует как «все дни» |
| Сенсор напряжения врёт (мВ вместо В) | Ток падает до минимума на всю ночь | Отбрасывает значения вне 175–280 В |
| У зоны нет отображаемого имени | Машина никогда не «дома» | Откатывается на идентификатор зоны |

## Уведомления

Три хука принимают произвольные действия:

| Хук | Когда | Доступные переменные |
|---|---|---|
| Старт сессии | зарядка включена | `soc`, `soc_valid`, `plan_source`, `needed_kwh`, `desired_current`, `hours_left`, `charger_status`, `cold_mode` |
| Завершение | зарядка выключена | те же + `stop_reason`, `target_missed` |
| Неисправность | см. таблицу ниже | `alarm_reason` |

Пример действия для хука завершения:

```yaml
- action: notify.mobile_app_phone
  data:
    title: Зарядка завершена
    message: >-
      {{ stop_reason }} — заряд {{ soc if soc_valid else 'н/д' }} %.
      {{ 'Цель не достигнута.' if target_missed else '' }}
```

Возможные значения `stop_reason`: `target_reached`, `charger_reports_charged`,
`fault`, `car_not_home`, `unplugged`, `window_end`.

Возможные значения `alarm_reason`: `charger_fault`, `car_refused_charge`,
`charger_reports_no_power_but_car_charging`, `no_power_while_on`,
`car_data_unavailable_check_integration_auth`, `car_data_stale`, `car_data_frozen`.

## Диагностика

Включите параметр **«Записывать ход зарядки в журнал»** — после каждого пересчёта
в журнале (Logbook) сущности выключателя появится строка вида:

```
план=soc | заряд=47.0% (не менялся 12.0 мин) | ёмкость 43.0 кВт·ч |
нужно 25.9 кВт·ч за 5.5 ч | U=207 В (sensor) × 1 ф |
уставка 14.0 → 16.0 А (возраст 1801 с), по факту идёт 12.8 А |
статус=charging | машина заряжается: yes
```

Этого достаточно, чтобы понять, почему ночью ток оказался не таким, как ожидалось.
Записи занимают место в базе — при постоянной работе параметр можно выключить.

### Частые вопросы

**Уставка 20 А, а станция показывает 18.3 А — это ошибка?**
Нет, расхождение нормально. Решение о перезаписи уставки сравнивает уставку
с уставкой, фактический ток в этом сравнении не участвует, поэтому дребезга
из-за него не будет. Недостачу поглощает обратная связь регулятора.

**Зарядка не стартует, хотя окно началось.**
Проверьте по порядку: сенсор статуса вообще читается (не `unknown`
и не `unavailable` — при нечитаемом статусе новая сессия не начинается);
статус не попал в список «кабель не подключён»; машина в зоне (или проверка
зоны выключена); сенсор доступности станции включён; не достигнут ли уже
целевой процент. Если план строится по энергии сессии — убедитесь, что указан
счётчик текущей сессии, а не накопительный за всё время.

**Станция игнорирует команды и заряжает по-своему.**
Заполните поле «Выбор режима зарядки». Внутренний планировщик станции
перебивает наши команды, если её не перевести в ручной режим.

## Разработка и тесты

Вся логика блюпринта живёт в блоке `variables:` и шаблонных триггерах. Это
позволяет проверять её без запущенного Home Assistant: тесты загружают YAML,
подставляют `!input`, рендерят каждую переменную по порядку против фейкового
набора сущностей и проверяют результат.

```bash
pip install -r requirements-dev.txt
pytest -m "not slow"    # 388 тестов, около 5 секунд
pytest -m slow          # мутационное тестирование, около 3.5 минут
```

| Файл | Что проверяет |
|---|---|
| `test_blueprint_structure.py` | Схема документа: все входы объявлены и использованы, дефолты в границах селекторов, порядок объявления переменных, `continue_on_error` на всех вызовах служб |
| `test_current_limits.py` | Жёсткие границы, дискретность, сужение диапазона атрибутами сущности, холодная погода, аварийный заряд с гистерезисом, число фаз, КПД |
| `test_voltage_sources.py` | Приоритет источников напряжения и отбрасывание неправдоподобных значений |
| `test_data_validity.py` | Три уровня достоверности данных и их приоритет, переключение плана, поправка на здоровье батареи, распознавание накопительного счётчика |
| `test_schedule_window.py` | Переход через полночь, дни недели, бюджет времени |
| `test_location.py` | Зоны, приезд посреди ночи, отличие сбоя GPS от отъезда |
| `test_decisions.py` | Матрица «заряжать / остановить», причины остановки, инвариант их взаимоисключения |
| `test_throttle_and_alarms.py` | Троттлинг команд, зона нечувствительности, контроль исправности |
| `test_triggers.py` | Шаблонные триггеры, в том числе на пустом наборе сущностей |
| `test_night_simulation.py` | Сквозная симуляция ночи в замкнутом контуре, включая приезд и отъезд машины, неисправность, потерю связи, мороз и watchdog |
| `test_mutations.py` | Проверка самих тестов: ловят ли они намеренно сломанный блюпринт |

Последний файл самый ценный. Он моделирует батарею и прогоняет регулятор
тик за тиком: выбранный ток определяет скорость наполнения, скорость наполнения
определяет следующий выбор тока. Так ловятся автоколебания, недозаряд и
избыточное число команд — ровно то, что не видно в тестах отдельных переменных.
Именно эта симуляция обнаружила, что при большой зоне нечувствительности ток мог
застрять в паре ампер от максимума и не дотянуть до цели холодной ночью.

### Мутационное тестирование

Зелёный набор тестов сам по себе ничего не доказывает — тесты бывают
бессодержательными. `test_mutations.py` намеренно ломает блюпринт по одному месту
за раз (23 мутации, каждая соответствует обещанию из этого README) и убеждается,
что остальной набор это замечает. Выжившая мутация означает, что соответствующее
поведение не покрыто.

Именно эта проверка нашла, что зажим тока применялся дважды и внутренний
маскировал внешний — ошибка проявлялась только когда максимум не делится
на дискретность, например 28 А при шаге 5 А.

Дополнительно `tests/validate_with_home_assistant.py` прогоняет блюпринт через
настоящий валидатор Home Assistant. Он вынесен из pytest намеренно: установка
Home Assistant тянет большое дерево зависимостей, а его внутренние API не имеют
гарантий стабильности. В CI этот шаг помечен как информационный.

Тестовый движок (`tests/ha_sim.py`) реализует только то подмножество шаблонного
API Home Assistant, которое реально использует блюпринт. Если блюпринт начнёт
использовать новую функцию, её нужно добавить в движок, а не ослаблять тесты.
